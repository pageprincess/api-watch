# APIWatch 留存策略

**作者**: Paul Graham (operations-pg)
**日期**: 2026-02-13

---

## 留存哲学

**获取带来用户。留存带来收入。**

对 APIWatch 来说，留存意味着：
- 用户持续回来查看
- 用户添加更多 API 监控
- 用户最终付费

---

## Week 1 留存目标

| 群组 | Day 1 | Day 7 | Day 30 |
|--------|-------|-------|--------|
| 注册用户 | 100% | 50% | 20% |

**转化**:
- Week 1 注册 10 个用户
- 5 个应该在 Day 7 仍然活跃
- 2 个应该在 Day 30 仍在使用

## 用户离开的原因（及如何解决）

### 原因 1: "它不工作"

**症状**:
- 用户注册，添加 API，再也没回来
- API spec 加载失败
- 没有收到告警（即使有变化发生）

**解决方案**:
1. **更好的错误信息**
   - "加载 spec 失败" → "Spec URL 返回 404。检查 URL。"
   - 内联添加故障排除提示

2. **成功的 onboarding**
   - 注册后立即发送测试告警
   - "你将在此邮箱收到告警。点击确认。"

3. **快速胜利**
   - 第一个 API 应该在 30 秒内工作
   - 用工作示例预填充（Petstore API）

### 原因 2: "我现在不需要"

**症状**:
- 用户说"很酷，但我现在没有任何破坏性变更"
- 再也没回来

**解决方案**:
1. **重互动邮件**
   - Week 1: "进展如何？需要帮助设置吗？"
   - Week 2: "新功能：AI API 模板"
   - Month 1: "你的每周 API 变更摘要"

2. **每周报告**
   - 即使没有变化，发送"本周无破坏性变更 🎉"
   - 保持 APIWatch 在用户心中

3. **价值展示**
   - 显示历史变化："本月此 API 变更了 3 次"
   - 即使什么都没坏也证明价值

### 原因 3: "太贵了"

**症状**:
- 用户使用免费层，达到上限，然后离开

**解决方案**:
1. **慷慨的免费层**
   - 3 个 API 对独立开发者足够
   - 每小时检查对大多数用例足够

2. **清晰的升级路径**
   - "你正在监控 3 个 API。升级获得无限。"
   - 显示具体价值："本月你本来会被通知 4 次"

3. **反馈折扣**
   - "给反馈，获得终身 50% 折扣"
   - "推荐朋友，两人都获得 1 个月免费"

## 参与飞轮

### 步骤 1: 第一次告警（"顿悟"时刻）

用户的第一次破坏性变更告警很关键：
- 它证明产品有效
- 它创造"救了我"的感觉
- 它创造社交分享材料

**如何加速**:
- 最初默认高频率检查
- 监控流行的 API（它们变更更频繁）
- 注册时发送"测试告警"让他们知道预期什么

### 步骤 2: 添加更多 API（"习惯"形成）

一旦用户从 1 个 API 获得价值，他们应该添加更多：
- "你在监控 Stripe。那 GitHub 呢？"
- 根据他们的技术栈建议
- 一键模板使其简单

**目标**: 平均每个用户 3+ API

### 步骤 3: 团队采用（"锁定"）

一旦一个人使用，他们会分享：
- "嘿团队，Stripe API 今晚在变化"
- "Slack 集成意味着每个人都看到告警"

**目标**: 1 个用户 → 3+ 团队成员

## 留存战术（Week 1-4）

### 即时（Day 1-7）

**对新注册用户**:
1. **欢迎邮件**（5 分钟内）
   - 来自创始人的个人邮件
   - "你在监控哪些 API？"
   - 提供帮助

2. **成功检查**（Day 3）
   - "你弄工作了吗？"
   - "有无法添加的 API 吗？"

3. **第一次价值**（Day 7）
   - "这是本周变化的内容"
   - 即使没有："本周无破坏性变更 🎉"

### 早期（Week 2-4）

**对活跃用户**:
1. **功能公告**
   - "新功能：AI API 模板"
   - "新功能：每周摘要邮件"

2. **升级推动**
   - "你有 2/3 API。升级获得无限。"
   - "用 Pro 获得 4 倍更快的告警"

3. **社区建设**
   - "加入我们的 Slack 给 API 开发者"
   - "分享你的 API 故事"

### 持续（Month 2+）

**对付费用户**:
1. **月度报告**
   - "APIWatch 本月为你节省了 X 小时"
   - "这些 API 变更了 Y 次"

2. **路线图透明度**
   - "我们接下来构建什么"
   - "对功能投票"

3. **个人检查**
   - 每季度:"进展如何？"
   - "什么会让这 10 倍更好？"

## 流失预防

### 流失前（信号）

**警告迹象**:
- 7 天没有添加 API
- 30 天没有收到告警
- 注册后从未登录

**干预**:
- 个人邮件:"一切都好吗？"
- 提供:"我可以帮你设置吗？"
- 折扣:"如果你留下，给你 50% 折扣"

### 流失后（赢回）

**邮件序列**:
1. Day 1:"我们注意到你离开了。一切都好吗？"
2. Day 7:"你可能喜欢的新功能"
3. Day 30:"最后机会：50% 折扣回来"

---

## 终极留存黑客

**让它成为他们工作流的一部分。**

APIWatch 应该被检查：
- 每次部署前（部署前检查清单）
- 期间事故（是 API 变更吗？）
- 站会期间（有任何 API 告警吗？）

**如何做**:
- 创建"部署前检查清单"模板
- 提供事故调查指南
- Slack 集成（状态检查）

---

## 流失指标

**如果到 Week 4**:
- Day 7 留存 < 20%
- Day 30 留存 = 0
- 平均 API/用户 < 1.5
- 零用户说"我会付钱"

**那么**: 产品市场契合度未实现。转型或停止。

---

**Paul 的建议**:

> 留存是价值的滞后指标。
>
> 如果你有良好的留存，你最终会有良好的收入。
> 如果你有糟糕的留存，你有一个漏水的桶。
>
> 在修复营销之前先修复产品。

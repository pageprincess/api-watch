# APIWatch 发布策略

**作者**: Seth Godin (marketing-godin)
**日期**: 2026-02-13

---

## 发布哲学

### Build in Public > Big Launch

不要搞盛大发布。不要等"完美"。产品永远不会完美。

正确的节奏：
1. 软启动给 50 个用户
2. 听取反馈，快速迭代
3. 当产品真的好用时，再告诉世界

**"Ship it" 比 "Perfect it" 重要**

---

## Phase 0: Pre-Launch（发布前准备）

### 准备清单

- [ ] 产品能实际工作（核心功能 100% 可用）
- [ ] 有一个真实用户故事（"我们帮 Alex 避免了 X"）
- [ ] 定价页面清晰透明
- [ ] 支持流程可用（哪怕只是创始人邮箱）
- [ ] 至少 5 个 API 模板测试通过

**不要发布时**：
- 功能还在开发中
- 定价页写着"Contact Us"
- 用户注册后看到空白页面

## Phase 1：第一个 50 用户（Week 1）

### 目标：50 个真诚的试用用户

### 策略：Reddit "Show and Tell"

详细策略见 `community-outreach.md`

### 发布时间窗口

- **最佳**: 周二到周四，美西时间 8-11 AM
- **避免**: 周五下午（周末启动），周一早上（周末 backlog）
- **理由**: HN 流量高峰期是上午 8-11 点

## 渠道 1：HackerNews（Priority #1）

**为什么**: HackerNews 是早期采用者的聚集地，API 敏感度高，真实反馈多

**时机**: 周二到周四，美西时间 8-11 AM（流量高峰）

**标题**:
```
Show HN: APIWatch – 在 API 变更破坏你的应用前告警你
```

**Hook 策略**: 聚焦具体问题（静默 API 变更）+ 反讽（我们都依赖 API，但没人检查变更）

**成功指标**: 100+ upvotes，20+ 评论

**后续行动**: 每条评论都回复，分享用例

### 为什么 HN 是首选？

1. **目标用户精准**：HN 用户 = API 重度用户
2. **反馈真实**：不会客气，会直接说"这没用"
3. **传播潜力**：好产品会被其他媒体 pick up

---

## 渠道 2：Reddit r/devops + r/programming

**为什么**: 精准的 DevOps 和开发者社区

**方法**: 有帮助而非推销。分享工具，请求反馈

**标题**:
```
我因为 Stripe API 静默变更导致生产故障，所以建了个监控工具

[Self-Post]
```

**成功指标**: 50+ upvotes，10+ 有建设性评论

### Reddit 发布的"潜规则"

- 不要发链接-only，要有实质内容
- 承认不足（"这是我第一个 SaaS"）
- 真诚请求反馈
- 回复每条评论

---

## 渠道 3：Product Hunt（Priority #2）

**为什么**: 验证、更大曝光、潜在媒体报道

**时机**: Week 2-3（HN/Reddit 反馈后）

**准备**:
- 30 秒演示视频
- 破坏性变更检测截图
- 清晰的 tagline

**Tagline**: "Monitor APIs for breaking changes before they break your app"

### PH 与 HN 的区别

| 维度 | HackerNews | Product Hunt |
|------|------------|-------------|
| 用户 | 工程师、早期采用者 | 产品爱好者、科技媒体 |
| 评判标准 | 技术价值、创新性 | 产品完成度、设计 |
| 生命周期 | 24 小时热度 | 全天累积 |
| 最佳内容 | 技术故事 | 产品演示 |

---

## 渠道 4：Twitter/X（持续进行）

**为什么**: 开发者社区、API 提供商、科技网红

**内容策略**:
- "API War Stories"（真实破坏性变更事故）
- Before/after 对比
- API 监控快速技巧

**Hashtags**: #API #DevOps #DeveloperTools #OpenAPI

### Twitter 内容日历

**周一**: "API Fail Friday"回顾（上周失败的 API 变更）
**周二**: 工具技巧（"如何监控 Stripe API"）
**周三**: 用户故事（"@user 用 APIWatch 避免了 X"）
**周四**: 行业观察（"为什么 API 变更悄然发生"）
**周五**: 轻松内容（"你的 API 监控配置对了吗？"）

## 风险与缓解

| 风险 | 概率 | 缓解 |
|------|------|------|
| HN 参与度低 | 中 | 积极回应每条评论；调整信息 |
| 生产环境 bug | 中 | 有回滚计划；快速响应 |
| 价值主张不清晰 | 低 | 已验证；聚焦"破坏性变更" |
| 竞品响应 | 低 | 快速行动；先发优势 |
